# `inspect` reports the declared timeline by observing frames, not by capturing them

## Context

An agent that wants to cut a scene, line a title up with a sound, or check that a clip still ends
where the track does has to read the timeline of a Composition. Today it can only read the source,
or render and look. The structure it wants is already data: the descriptor declares the audio clips
as frame counts (the [audio muxing decision](../../render/adr/20261026-audio-track-muxing.accepted.md)),
and named Sequences report the half-open frames they show (`sequences()` on the page, which the
[preview](../../preview/CONTEXT.md) already uses to label its scrub bar).

The CLI's `inspect` has been a reserved name since the [output contract](20261024-cli-output-contract.accepted.md),
whose agent term says "without rendering video". Two things make that phrase need a decision.

- A named Sequence is registered only while its parent is mounted, and a parent shows only its own
  frames. The mounted tree is therefore the only source of the Sequence list, and the list is
  frame-dependent: reading one frame can miss a Sequence that exists at another.
- The Composition's component is user code. It cannot be evaluated in Node, so any read of the
  tree happens in the browser realm the renderer already owns.

User-declared markers (a way for the author to attach labelled instants, such as a beat grid or
cues) were considered for the same command. The product owner decided option (C) of TASK-250: ship
`inspect` for the Sequences and the audio clips first, and take markers up in a separate task once
real use has settled them. They are out of scope here because they would be a new authoring API,
with open questions about continuous values such as a gain curve, and the questions above do not
need them.

## Decision

### "Without rendering" means without capturing

`inspect` mounts the Composition in the renderer's browser realm, as every other command does, and
settles its frames there; it never takes a screenshot, never encodes, and never writes a file. The
sentence in the term is read as "without producing an image or a video", not as "without a browser".
This is the only way the Sequences can be known, and it costs a page load plus the settle of each
frame, not a capture: the picture is the expensive part of a frame, and it is the part `inspect`
leaves out.

### One observation per frame, over every frame

A frame is observed, not captured: `CaptureFormat` gains `{ type: 'none' }` (`observeCapture`). The
frame job runs the same ownership protocol (settle, grant, validate, complete) with the same
deadlines, cancellation and re-settling on a changed version, and at the point where it would take
the screenshot it reads `sequences()` instead. The result carries `sequences` and an empty `image`.
Reusing the job keeps one implementation of "the frame is committed" and means an observed frame is
rejected, re-settled or timed out by exactly the rules a captured one is.

`inspect` observes every frame from 0 to the Composition's frame count, dealt across
`--concurrency` renderers by the same pool `render` uses, and takes the union of the spans seen. An
exhaustive scan is deliberate: a Sequence is visible only through a frame that mounts its ancestors,
and sampling could miss a short one without any signal that it did. The cost grows with the frame
count, so a long Composition pays in proportion; a ranged scan (`--from`/`--to`) is a possible
follow-up and changes no part of the contract below.

### Audio comes from the declaration

The `audio` list is read from the descriptor and needs no frame. Each clip is reported with the
defaults applied: `startInFrames` (0), `endInFrames` (the declared end, or the Composition's end),
`offsetInFrames` (0) and `volume` (1), plus the same instants in seconds. The span is clipped to the
Composition, because the mix is cut there, and a clip that starts at or after the end has an empty
span. `endDeclared` says whether the end came from the declaration: when it is `false` the clip plays
to its source's natural end, which `inspect` does not measure (it would need `ffprobe` on every
source and would make `inspect` fail on an unreadable file), so `endInFrames` is then the latest the
clip can be heard. A missing or unreadable file is not an `inspect` finding; `render` reports it.

### Frames and seconds

Every instant is reported as a frame and as seconds. Frames are authoritative; seconds are derived
through the Time Module (`frameToTime`, `toSeconds`), the only frame-to-second conversion, so they
are exact for rational rates such as 30000/1001.

### Contract

`inspect` is a new `data` member of the envelope (`format: 'inspect'`; `schemaVersion` stays 1, an
added command is compatible). `sequences` is ordered by start frame, then path (outer first), then
end frame; two Sequences equal in every field are listed next to each other. A Sequence's `path` lists its
named ancestors outer to inner and ends with `name`; unnamed Sequences add no segment.

A Sequence is reported **as placed**: `startFrame` and `endFrame` (and their seconds) are not
clamped to the Composition. A Sequence authored with `from={-0.5}` has a negative start (and negative
seconds), and one placed past the end has an end beyond `durationInFrames`. The schema therefore
allows negative frames and seconds in a Sequence entry, and nothing else in the data. This differs
from the audio on purpose. An audio span is what the mix contains, so it is cut at the Composition,
because nothing outside it is heard. A Sequence is a placement the author wrote, and the
placement is what an agent edits; clipping it would hide that the Sequence starts before frame 0
or never shows, and would change a value the agent has to type back. A consumer that wants the
visible part intersects the entry with `[0, durationInFrames)`.

Same-named siblings with the same frames are different Sequences and stay separate entries: a frame
lists every Sequence mounted at that moment, so the entry count is the largest count any one frame
listed. `ok` follows the
envelope rule; a Composition that fails to mount, to settle a frame, or whose props fail validation
reports the same diagnostics as any other command and no `data`.

`--props` is honoured, because props can change which Sequences exist. `--concurrency`,
`--project-root`, `--vite-config`, `--software-webgl`, `--disable-sandbox`, `--verbose` and `--quiet`
mean what they mean for `render`. `--composition` selects the Composition as it does for `render`. Warnings the observed frames raise are not forwarded: `inspect` makes no claim about
rendering them, `check` and `render` do. `validate` stays reserved.

## Consequences

- A Composition whose frames are slow to settle (large assets, heavy WebGL) is as slow to inspect as
  to render without encoding. The command is still cheaper than a render by the screenshot and
  encode of each frame, and it writes nothing.
- What `inspect` reports is every named Sequence the tree **registers** at some frame in
  `[0, frameCount)`. A Sequence registers while it is mounted, whether or not its own interval
  contains that frame, so a top-level one placed outside the Composition (before frame 0 or after
  the last frame, as with `from={5}` in a 1 s Composition) is reported with its placement. A nested
  one is mounted only while its parent Sequence shows the frame, so it is reported if some observed
  frame lies inside every ancestor, and its frames are the part its ancestors show. What cannot be
  reported is a Sequence that no observed frame mounts: one inside a conditional branch no frame
  takes, or under a parent whose own frames lie wholly outside the Composition. As far as the page
  is concerned such a Sequence does not exist, and only the source could reveal it.
- The audio and the Sequences answer different questions (what is heard, where it is placed), and so
  they treat the Composition's edges differently, as the Contract section says.
- The `none` capture is internal to the render context; the CLI exposes no flag for it.

## Alternatives

- **Evaluating the Composition in Node, or reading the source**: rejected. The component is user
  code that needs the browser realm, and the source does not say which Sequences a given set of props
  mounts.
- **Sampling frames** (the boundaries of the audio, every Nth frame): rejected as the default. A short
  or late Sequence could be missed without any signal, and a scan that sometimes lies is worse than a
  slow one. The exhaustive scan costs frames, not pictures; a ranged scan stays open as a follow-up.
- **Capturing the frames and discarding the pictures** (reusing `render` or `frame`): rejected. It pays
  the screenshot, the expensive part of a frame, for nothing, and the spec for "without rendering"
  would be a lie. The observation mode keeps one frame protocol instead of a parallel mechanism.
- **A separate page-side query that walks the tree once**: rejected. A Sequence is only registered
  while its ancestors are mounted, so one mount shows one frame's worth of the tree; it would need the
  same per-frame seeking, with a second implementation of "the frame is committed".
- **Measuring audio with `ffprobe`**: rejected for now. It would make `inspect` need FFmpeg and fail on
  an unreadable file; `endDeclared` marks the one value that depends on it.
- **Clipping Sequences to the Composition, like audio**: rejected, for the reason given in the
  Contract section.
- **Declared markers in the same command** (option (A) of TASK-250): out of scope by the product
  owner's decision (C).
