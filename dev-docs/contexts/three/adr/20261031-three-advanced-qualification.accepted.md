# Qualify advanced three and GPU behaviour feature by feature, and fail a frame whose shader program does not link

## Context

The [capability ADR](20261031-three-canvas-capability-api.accepted.md) shipped `ThreeCanvas` and `CameraRig` and left R10 of the [accepted time-control decision](../../../decisions/20261024-time-control-and-frame-capture.accepted.md#r10--qualify-advanced-three-and-gpu-behavior) to TASK-185: controls and damping, physics, `AnimationMixer`, stochastic and feedback shaders, temporal postprocessing, shadows, WebGPU and XR, asynchronous shader compile and upload errors, multiple canvases, asynchrony from React and StrictMode, and context loss after readiness. Its "Not in scope" named part of that set and added a render-target GPU strategy; it did not name stochastic shaders, upload errors, multiple canvases or React `StrictMode`.

The forces are the tier definitions, not taste. A claim is either **Qualified** — a test in the `three-dom` project proves it, byte-identical pixels across sequential, shuffled/repeated and fresh-mount frame orders for B, a `seek.uncontrolled` warning for C, a specific Diagnostic for a failure — or **Excluded**, with the reason and what an author should do instead. "Probably works" is not a tier. The `three-dom` project is headless Chromium on SwiftShader inside one pinned environment, so every claim below is same-environment byte equality, never cross-GPU equality ([R14](../../../decisions/20261024-time-control-and-frame-capture.accepted.md#r14--measure-broader-rendering-portability-and-cost) stays open). The library facts every row relies on are collected in [three 0.186 and R3F 9.8 behaviour](../knowledge/three-0.186-renderer-behaviour.md).

### Shader programs

`ThreeCanvas` assigns `renderer.debug.onShaderError` after creation. Assigning that callback replaces three's own console report, so the callback reprints the program info log and both shader info logs, and latches a failure in the canvas settlement; `settle` advances, fences with `gl.finish()`, and then returns a failed `Result` carrying `render.page-error`. The callback receives no material, so unlike three's default report it cannot print the material name or type, and the Diagnostic is generic: a Composition with several shader materials has to identify the failing one from the info logs.

- The code is **reused, not added**. The failure is a page-level three error that a host cannot repair by configuration, and the agent-facing distinction is already carried by the message ("A shader program failed to compile or link while settling the frame.") and the hint ("Fix the shader material; a program that does not link renders nothing, so the frame cannot be captured."). Adding a code would grow the `DiagnosticSchema` enum, its JSON Schema and two guide tables to separate a failure the CLI cannot handle differently.
- The latch is **sticky**: three checks a program inside `WebGLProgram.onFirstUse`, which runs on `getUniforms()`/`getAttributes()` during the first render of the material and never again. A failure forgotten after its frame would let every later frame publish a scene the program does not draw.
- `KHR_parallel_shader_compile` and `compileAsync()` change nothing here: the link check does not run in `compile()`, only at first use, and rendering locks on the program anyway. No `compileAsync()` call is added, and `gl.finish()` remains the fence.
- `debug.checkShaderErrors` must stay at its default `true`; three performs no check at all when it is disabled. `ThreeCanvas` owns `debug.onShaderError` for the same reason it owns `preserveDrawingBuffer`, and because `onCreated` runs after the assignment, a caller who assigns the callback afterwards takes the detection away deliberately.

### Texture uploads

_Added 2026-11-09 (TASK-256)._ three has no upload callback and never checks `gl.getError()` after an upload; it warns on the console and renders the material with an empty texture. The canvas reads three's own record of what it uploaded instead of the console. After `advance` and `gl.finish()`, `settle` walks the visible objects of the scene, collects every texture a material holds (any material property, and `ShaderMaterial` uniforms, single or in an array) and fails the frame when a texture is in one of two states:

- **Marked for upload and never uploaded**: `texture.version > 0` and `renderer.properties.get(texture).__version !== texture.version`. `WebGLTextures.setTexture2D` skips the upload exactly when the image is `null` (`no-image`) or `image.complete === false` (`image-incomplete`), and `uploadTexture` is what records the version, so a mismatch after the upload was attempted means the upload did not happen (`not-uploaded` for any other cause). three attempts an upload only when a draw samples the texture, so the canvas attempts every checked upload itself first with `renderer.initTexture(texture)` (the same `setTexture2D` path as a draw, idempotent, and it unbinds afterwards). Without that, a valid texture would read as not uploaded whenever no draw sampled it: a frustum-culled object, `Material.visible = false`, a layer the camera does not render, a `ShaderMaterial` uniform the shader never reads. And the record persists across frames, so the verdict would depend on whether an earlier frame had drawn the object, which a frame that is a pure function of time cannot allow.
- **Uploaded with no pixels** (`empty-image`): an `HTMLImageElement` that failed to decode reports `complete === true` and 0x0, which three uploads without a warning (the browser raises `GL_INVALID_VALUE`). A zero `width` or `height`, or a missing cube face, is an empty image.

The Diagnostic is `render.page-error` (reused, for the reason the shader failure reuses it), names the first texture (`Texture.name`, the property, the object and material names) in the message and lists every failed texture in `details.textures` with its `reason`. Nothing random is in it: a texture's `uuid` is not reported.

- The check is **stateless, not latched**: a failed texture keeps a mismatching version (or its empty image), so every later frame fails with it until the author fixes the texture. A shader failure needs a latch because three checks it once; an upload does not.
- It reads `renderer.properties` (typed `unknown`, key `__version`), which is three-internal. `texture-upload.test.ts` and the browser tests, which include a negative control with an uploaded `DataTexture` and a decoded image, fail on an upgrade that changes it, so it is a checked dependency like the subscriber count.
- A texture with `version === 0` is skipped: the author never marked it for update, three uploads nothing and says nothing, and that is an unfinished texture rather than a failed upload. Render-target, video and external textures are skipped because something other than an author's image drives them.
- Only objects with `Object3D.visible` are walked (`traverseVisible`; scene state, so deterministic). Whether a draw samples the texture does not matter, because the upload is attempted by the check: the camera frustum, `Material.visible`, layers and shader use are not consulted. A broken texture on such an object fails the frame even if it is never on screen (it would show the moment it moves in); a valid texture on it never does, and the verdict is the same whether the frame is sought fresh or after other frames. Textures of an invisible object (`Object3D.visible = false`) are not checked.
- A loader error (`useLoader`/`useTexture` with a 404) is not this check: the loader throws, the Composition's error boundary catches it and the frame fails as a Composition error. This check covers textures built by hand (`new Texture(image)`) and images a loader resolved but could not decode.
- **Not detected**: an upload three accepts and the GPU rejects, for example a `DataTexture` whose data is shorter than its size (`GL_INVALID_OPERATION`) or wider than `MAX_TEXTURE_SIZE` (three only warns). Their versions match, so only `gl.getError()` shows them.

### Context loss and recovery

A lost context is detected after the fence (`gl.isContextLost()`), so the frame fails with `render.page-error` rather than capturing whatever the lost context left behind. Recovery stays excluded, and a recovery would need, at least: three to re-initialize its `WebGLState` and extensions (`webglcontextrestored`), every geometry, texture, render target and program re-uploaded or recompiled, shadow maps and post-processing chains rebuilt, the frame generation re-settled inside the same deadline, and a test proving the restored frame byte-equals the frame a fresh context renders. Chromium restores a lost context by itself in this environment on a later GL use, and a simple scene then rendered bytes identical to before, which is exactly why a claim needs the whole list rather than one observation.

### Upgrades

`r3f-contract.browser.test.tsx` fails on an R3F upgrade that changes any of: `state.advance(timestamp, false)` renders exactly once and only that root, `frameloop="never"` never renders on its own, the module-level `advance(timestamp, true)` is what flushes global effects and every root (which a canvas must never use), `state.internal.subscribers` is an array whose length counts `useFrame` subscribers, and `useFrame` receives the timestamp delta. R3F 9.8.2 also still constructs the deprecated `THREE.Clock`, which is why `clock.elapsedTime` is pinned rather than treated as an implementation detail.

## Consequences

- `pnpm test` runs `three-dom` in about 5 s on macOS arm64 with SwiftShader (39 browser tests in 7 files); the cheap half of the failure claims runs in the `unit` project against `createCanvasSettlement`, without a renderer.
- Tier B pixels are compared byte-exactly, and the fresh-mount pass opens one mount per claimed frame and renders that frame first, so state an earlier render left in the same mount cannot pass as order independence. The pass also reports the mounts it opened and every render each one ran: every Tier B claim and `camera-damping.browser.test.tsx` require one mount per claimed frame with that frame as its only render, so a refactor back to a shared fresh mount fails a test instead of leaving the suite green. The damped scene must also report a mismatch, so a claim that passes the pass is measured against one that can fail.
- A shader that does not link now fails a render that previously produced a frame with the material missing. That is a behaviour change for a Composition with a broken shader, and it is recorded in the CHANGELOG.
- Shadows rely on `shadowMap.autoUpdate` staying at its default `true`: the map is rendered on every `advance`, which is correct for absolute time and costs one shadow pass per frame.
- On three 0.186, R3F's boolean `shadows` maps to the removed `PCFSoftShadowMap`; three warns once and falls back to `PCFShadowMap`, so the shadow tests use `shadows` and still pass, and `shadows="percentage"` is the warning-free spelling.
- `AnimationMixer` is qualified only inside the clip: a `LoopOnce` action that reaches its clip duration is disabled by three, so that update applies no value and the previous pose survives. Keep the clip at least as long as the claimed frame range, or use `LoopRepeat`, and do not claim the frame at the clip's end.
- Nothing here qualifies asynchrony from React `StrictMode` (double-invoked effects and double-mounted canvases), which R10 lists and TASK-185 does not cover. It stays open.
- _Amended 2026-11-09 (TASK-257):_ the lost-context, shader and texture Diagnostics carry `location` (`compositionId`, `frame`, `timeSeconds`), as the [time-control decision](../../../decisions/20261024-time-control-and-frame-capture.accepted.md#failure-diagnostics) asks. `createCanvasSettlement(compositionId)` builds it per settled frame with the runtime's `frameLocation`, the same function the runtime uses for its own Diagnostics. The shader latch stores only the fact of the failure, not a Diagnostic, so a later frame fails with its own location rather than the frame whose render first hit the program.

## Alternatives

- **A dedicated `render.shader-error` code:** clearer to grep, but it is the same page-level failure for every host, and the code set is a public contract with a generated JSON Schema and guide tables. Revisit when a host has to branch on it.
- **Checking `gl.getError()` after each advance for the upload (TASK-256):** it would also catch the GPU-side rejections that are not detected above, but it cannot name the texture, it reports any GL error from any source in one undifferentiated Diagnostic, and whether the error state is empty for every valid scene on other GPUs and drivers is unmeasured here (it is empty in the `three-dom` SwiftShader runs). Not added; reopen with a measurement across environments.
- **Hooking `console.warn` for three's `Texture marked for update` warnings (TASK-256):** it reads the same condition as the version check, but a console hook is global to the page, ordered against other canvases and three's own warning text, whose wording is three's, not an API, and it never covers the `empty-image` case, which three does not warn about. The version record is state, not output.
- **Letting three log and continue:** that is the defect this task closes: three logs `THREE.WebGLProgram: Shader Error` to the page console, which the renderer never forwards, and draws the scene without the material.
- **Calling `renderer.compileAsync()` before each advance to surface errors earlier:** it waits for `KHR_parallel_shader_compile` readiness but does not run the link check, adds a polling loop per frame, and the first-use stall remains.
- **Recovering from a lost context by re-settling:** plausible, unmeasured, and it would publish a frame from a resource set nothing has verified; excluded until the list above is implemented and tested.
- **Wrapping drei's `OrbitControls` so it takes a time input:** damping integrates from the previous pose; a wrapper would rename the tier instead of removing the history. `CameraRig` stays the absolute alternative.
- **A physics engine with a seeded step count:** a replay would have to re-simulate from frame 0 for every seek, which is a different feature (a deterministic bake), not a canvas integration.
