# Declare a named Composition registry with schema-owned defaults

## Context

TASK-153 records the user's accepted decision of 2026-10-24: an entry registers several Compositions, each with a unique string id, Zod props schema with defaults, width, height, rational FPS, and duration. `--composition <id>` selects one; omission is allowed only for a singleton registry, and an unknown id uses `cli.composition-not-found`. `inspect` needs enumeration, and excluding the registry from Foundation provides little benefit. This ADR fixes the API and validation questions without re-evaluating that decision.

[core](../CONTEXT.md) owns Composition and the shared Composition runtime; [agent's contract](../../agent/adr/20261024-cli-output-contract.accepted.md) owns Diagnostics and CLI envelopes. Schemas/components cannot cross the Node/page boundary as plain data.

## Decision

The package root exposes `defineComposition({ id, component, schema, width, height, fps, durationInFrames })` and `defineCompositions([...])`. The entry exports the immutable registry as **`export const compositions = defineCompositions([...])`**. Preserve heterogeneous schema/component type inference, declaration order, and exact case-sensitive ids. Reject empty/duplicate ids and an empty registry. Registration has no global side effects and does not require rendering a JSX tree to enumerate it.

Width/height and FPS numerator/denominator are positive safe integers; `durationInFrames` is a nonnegative safe integer and the single duration authority. The Time Module computes time and validity on `[0, durationInFrames)`. A zero-duration registry entry can be inspected but not captured. Props do not recompute metadata in Phase 1.

`Composition` is the selected tree's Composition runtime provider/root, not the registry declaration mechanism. Its `compositionRuntime` prop is the realm-local explicit-time coordinator; `compositionRealm` names the owning page/iframe. `listCompositions()` returns plain ordered metadata; `mount({ compositionId, props, revision })` selects the page-local definition, validates it, and constructs the selected tree. Neither operation serializes React components or Zod schemas to Node. The exact flow and example are in the [Design Doc](../../render/design-doc/20261024-composition-loading.md#registry-api-and-selection).

Zod is the sole source of defaults: the schema accepts `{}` and produces JSON-valued object defaults. There is **no separate `defaultProps` field** to merge or keep synchronized. At declaration, reject non-empty component `defaultProps`, including inherited class statics and function properties, with `render.page-error` naming the component and explaining that schema defaults are the only defaults authority. Reject unreadable/accessor `defaultProps` defensively through descriptor inspection: getters execute zero times even across repeated declarations, whether they throw or return empty defaults. Absent, null/undefined or empty data defaults are allowed; inherited enumerable keys inside a defaults object make it non-empty. Validate each wrapper's defaults and recursively unwrap `memo` through its inner component and `forwardRef` through its render function, applying the same validation at every layer. Reject `lazy`, including inside `memo`, at declaration with `render.page-error` naming the `component` field, explaining that a lazy component cannot be validated before it resolves, and hinting to lazy-load inside the component instead of the registry entry. Never resolve or execute its lazy payload. The CLI checks JSON syntax/object shape, then sends raw JSON to the page. Use `safeParseAsync` on the actual schema before mounting; cache successful defaults validation per registry revision and validate supplied props once per mount/props revision, never per frame. Concurrent defaults checks share in-flight work; a failed or expired check is evicted so a later check can retry with a corrected budget. Pass raw props directly to the schema; missing values use Zod defaults and explicit values follow its policies. Check that parsed output is also a JSON-valued object before checking reserved names: null, undefined, arrays and primitives at the root fail with `composition.props-invalid`, not `render.page-error`. Reject cycles, exotic objects, accessors, symbol/non-enumerable keys, bigint values anywhere and non-index array properties. Ordinary and null-prototype objects are accepted at the root and nested; rebuilding preserves their data, not their prototype. Rebuild the schema output from own data descriptors, validating every retained value (including nested own `__proto__` data) rather than relying on a record validator that can skip keys. Prepared props hold that rebuilt, checked JSON tree. The component receives deep-equal checked values with shared nested references, but not top-level reference identity: `createElement` constructs a new top-level props object. Reject top-level own `key`, `ref`, `__self`, `__source` and `__proto__` with `composition.props-invalid`, naming the field in the message and hint: React consumes or copies these names and cannot deliver them faithfully. These names remain valid nested JSON data. Restart the configurable 30-second loading timeout for every defaults or supplied-props parse, including later mounts: it covers `safeParseAsync`, JSON-output validation and issue/error conversion, plus root/viewport preparation and mount acknowledgement for selected props. A defaults parse ends on its validation result. Expiry fails with `render.page-error`, never an abort or a frame timeout; default producers/refinements must be deterministic.

Schema validation failures use `composition.props-invalid` and sanitized JSON Zod issues. Invalid duration uses `composition.duration-invalid`; invalid width, height or FPS and other declaration/loading exceptions use `render.page-error`. `composition.props-invalid` is reserved for props-schema validation, not metadata: TASK-154 converts `createFrameRate` failures to `render.page-error` at the declaration boundary, and TASK-157 preserves that mapping in transport. Malformed CLI JSON/non-object values and ambiguous omitted selection use `cli.invalid-arguments`; an explicit unknown id uses `cli.composition-not-found`. `inspect` enumeration is not a request to mount and does not require selection. The [Design Doc](../../render/design-doc/20261024-composition-loading.md#props-validation-before-mounting) defines error conversion and default/unknown-key behavior; no new Diagnostic codes or details payloads are introduced.

## Consequences

TASK-154 implements the registry and provider together with the shared Composition runtime implementation. Its older `defaultProps` wording must become schema-owned defaults, and `durationInFrames` remains canonical rather than adding conflicting seconds. core needs Zod as well as React/ReactDOM and shared utilities; Zod is already a production dependency. No new dependency is added by this record.

Enumeration executes trusted entry/schema code in the browser but does not mount all scenes. Node does not need to evaluate TSX or reimplement schema refinements. Non-JSON/function/ReactNode props remain component-internal TypeScript concerns rather than CLI inputs. Future JSON Schema inspection describes the structural schema and cannot replace authoritative page validation.

## Alternatives

- One default React export: already rejected by the user because it prevents multi-Composition enumeration and selection.
- JSX-only discovery or global `registerRoot`: unnecessarily executes a discovery tree or introduces import-order/global state.
- Independent `defaultProps` plus Zod defaults: creates two defaults authorities and ambiguous nested merging.
- Node-import the TSX/schema or validate only a generated JSON Schema: duplicates browser/config resolution and cannot represent every Zod refinement's semantics.
