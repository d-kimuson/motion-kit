# Bundle Vite 7 as a production dependency and load the user's configuration

## Context

TASK-153 records the user's accepted decision of 2026-10-24: motion-kit supplies Vite, runs it in middleware mode from `src/render`, and loads the project's `vite.config.*` when present. Users need neither a Vite installation nor a second bundler configuration. HMR and the shared preview/render loading contract motivate this choice; this ADR does not reopen it.

The open version/install-policy question must respect [local development](../../../guidelines/local-dev.md), including exact pins, the 1440-minute release-age floor, and the production [license allowlist](../../../../scripts/check-licenses.ts). See the [isolated dependency evidence](../knowledge/20261024-vite-loading-cost.md).

## Decision

Use **Vite major 7**, initially **`vite: "7.3.7"` in production dependencies** when TASK-157 implements loading. Import that dependency from the Node-only loading service. It is neither an optional peer nor a root browser export. No package/lockfile changes are required in this design-only task: isolated installation verifies the decision without shipping unused code/dependencies.

Vite 7.3.7 is MIT, published 2026-10-06, older than the release-age floor at this decision. Its clean platform-resolved production closure passes the existing license checker without exceptions. Node's supported range is `^20.19.0 || >=22.12.0`, compatible with the repository's Node 26. Vite 8.3.5 is not chosen: its mandatory `lightningcss@1.33.0` is MPL-2.0 and the isolated closure fails the current allowlist. Do not add a licensing exception or substitute an unreviewed major to obtain a newer server.

The user's own Vite, including a different major, can coexist in their dependency tree. Never replace it, override all Vite versions, or select it as motion-kit's server. Load their config through `loadConfigFromFile` only after installing ESM/CommonJS module-resolution interception in the loading child: config and plugin imports of bare `vite` and supported public `vite/*` resolve exclusively to bundled 7.3.7, including externalized dependencies. User plugin packages still resolve from the project; a config importing Vite must work when the project has no Vite installed. The loading-service config-loader adapter also intercepts Vite's config-bundling/externalization resolver before project lookup, aliasing those specifiers to the bundled package. Unmodified `loadConfigFromFile`, `resolve.dedupe` or Node hooks installed only after bundling are insufficient. Interception does not adapt Vite 8 APIs or cover private/absolute imports, plugin-spawned processes or custom loaders; these are unsupported, and detected bypasses fail rather than load a second Vite. The loaded user config is passed to the bundled Vite unchanged, except motion-kit's reserved settings, which are overridden after resolution per the Design Doc's precedence table: middleware/custom `appType`, the loopback listener, entry routes, no `open`, host-controlled HMR, React/runtime singleton resolution, the stderr logger, and `configFile: false`. Keys that do not apply to middleware serve mode (`build`, `preview`, `test`, `worker`, and unknown keys) are simply ignored by Vite, as they always are, while the `optimizeDeps` options its dependency optimizer consumes, including `esbuildOptions`, do apply: motion-kit never rejects a key and never maintains a key list. A top-level `ssr` block is not ignored: during serve Vite merges it into the `ssr` environment, and the loading policy then overrides that environment's `resolve.alias` and `resolve.dedupe` with motion-kit's, leaving its other options in place. Plugins are passed through; motion-kit does not read plugin manifests, peer ranges, or Vite internals. Loading failures are reported by what failed, not by the phase in which Vite surfaced it. A throw inside Vite config resolution or a project plugin hook is `render.page-error` whose message names the culprit and the bundled Vite version and whose hint names the config file path and states that the project's plugins must work under Vite 7; a missing optional preprocessor and a detected second Vite name their own cause the same way. Vite's dependency optimizer gets its own message: it carries no `plugin` field and is recognised only by its `Error during dependency optimization` banner, ANSI styling or not, and it pre-bundles the project's installed dependencies as well as consuming the config's `optimizeDeps`/esbuild settings, so a rejection proves neither. That message names the bundled version, and its hint names the config file path and both possible causes — those `optimizeDeps` settings, or a dependency (for example one whose own `require` cannot be resolved) — so an ordinary broken/optional-peer dependency is not blamed on the project's `vite.config.ts`. Everything else keeps the plain loading Diagnostic, which names the bundled version but no config path: server creation, the HTTP/Vite service, the shell, the loopback bind, and Vite's own plugins (`vite:css`, `vite:esbuild`) failing inside a transform. Raw exception text and stacks never enter a Diagnostic. _Amended 2026-10-24:_ the original text required rejecting non-7 plugins (including `@vitejs/plugin-react@6`), unsupported or nested config keys, and missing optional preprocessors by name; this is superseded by the TASK-157 product owner scope bound on Vite configuration compatibility, which treats the project's config and plugins as trusted code. Preview and rendering both use serve/development semantics; differences in host supervision/HMR do not choose a second scene build.

Follow the [Design Doc's configuration precedence](../design-doc/20261024-composition-loading.md#vite-configuration-and-entry-loading): retain user aliases/plugins, CSS/assets/root/base, but reserve the Composition runtime bootstrap, singleton resolution, middleware/listener, logging, and host-controlled HMR. Built-in TSX transformation suffices without requiring a React plugin.

Patch/minor changes are deliberate exact-pin updates with lockfile, license and loading/compatibility tests; a major upgrade requires revisiting this ADR and publishing its compatibility impact. Preserve `minimumReleaseAge: 1440`; do not bypass it for the implementation install.

## Consequences

Users install a working renderer toolchain without installing/configuring Vite. Browser consumers do not import Vite, but installing the single package still pays its production dependency cost; an export boundary is not an installation-size boundary. The clean macOS arm64 probe occupies **18,792 KiB (~18.4 MiB)** for the platform-resolved dependency store, excluding pnpm's shared store, browser binaries, user plugins, and optional preprocessors. Vite's own npm unpacked size is **2,244,268 bytes (~2.14 MiB)**. Other platforms and package-manager deduplication change the incremental cost; a different user Vite can increase duplication.

The future implementation must rerun the production license check on its actual lockfile/platform closure and qualify user-plugin interoperability, linked-package React deduplication, and config root/base behavior. A maintained older major is a deliberate licensing/compatibility tradeoff, not a claim that all Vite 8 projects work unchanged. The product owner has been informed through the team channel of the Vite 7 pin, plugin compatibility requirement and ~18.4 MiB footprint; these are settled inputs, not an outstanding approval gate.

## Alternatives

- Custom bundler: already rejected by the user as duplicating mature bundler/configuration/HMR functionality.
- Mandatory user-managed Vite or optional peer: conflicts with the user's no-setup decision and makes the ordinary CLI path installation-dependent.
- Dynamically choose the project's major: makes the protocol's server behavior vary by project and transfers compatibility obligations to every caller.
- Vite 8.3.5: mandatory MPL-2.0 dependency fails the current allowlist; a license exception is not part of TASK-153.
