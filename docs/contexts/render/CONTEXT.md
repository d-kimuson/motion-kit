# render

Frames and files. render runs a Composition in Chromium through Playwright, waits for readiness, captures each frame, and encodes the result. It is the only context besides agent that uses Node.js APIs.

## Ubiquitous Language

| Term              | Code             | Definition                                                                                                                                                         |
| ----------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Renderer          | `createRenderer` | Builds the host object exposing `renderFrame({ frame })` and `renderFrames({ from, to })`; each frame computes time, waits for readiness, captures.                |
| Readiness Barrier | `settleFrame`    | The page operation that seeks/commits and drains generation-tagged content and integration acknowledgements into a ready lease; never a timer.                     |
| Capture           | `capture`        | The transport step that screenshots the settled page via `page.screenshot`, inside the host frame deadline.                                                        |
| Encoder           | `Encoder`        | The port that turns the captured frame stream into an MP4 file; see the [system FFmpeg ADR](adr/20261025-system-ffmpeg-encoder.accepted.md).                       |
| Audio Track       | `AudioTrack`     | One clip a Composition declares as data (`src`, `startInFrames`, optional `endInFrames`/`offsetInFrames`/`volume`); the encoder muxes it by frame-derived seconds. |

TASK-157 implements supervised loading, frame transport and PNG capture over core's shared registry/provider/coordinator. Encoding and the asset acquisition API remain separate tasks.

| Term            | Code                              | Definition                                                                                                                                                                      |
| --------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Loading session | `src/render/loading`              | One supervised Vite/configuration module graph and HTTP service reused for one project/entry/host mode within a CLI invocation.                                                 |
| Host mode       | `source: 'renderer' \| 'preview'` | The owning host's mode. Sessions and Composition realms are never shared between modes; each capture lease records its source so duplicate or cross-source claims are rejected. |
| Page settlement | `settleFrame`                     | The page operation that seeks, commits and settles without capturing; returns a discriminated `ready` / `failed` / `aborted` result. It is not `renderer.renderFrame`.          |

## Invariants

- A frame is captured only after the Readiness Barrier passes; a timed wait is not readiness.
- Within supported A/B paths and a fixed qualified environment, rendering frames in any order produces the same files as rendering them in sequence; detected Tier C emits `seek.uncontrolled` instead of a determinism claim.
- The [loading contract](design-doc/20261024-composition-loading.md) uses bundled Vite 7.3.7 and the named Composition registry. Node-owned shell/entry generators do not enter the browser import graph.
- Settlement retains the capture lease until the host validates capture; resource-version changes re-settle under the original deadline, while cancellation aborts without publication.

## Shared runtime handoff

Consume core's `PreparedComposition` and `createCompositionRuntime`; do not duplicate schema parsing, frame generations or readiness in the renderer. Core's `mount` prepares validated props without rendering content; the first owned frame triggers the selected tree. A ready lease is not a release. Reject publication unless `completeCapture` accepts it; on `resettle`, discard pixels and retain the generation and original host deadline.

TASK-157 owns loading supervision (including root/viewport preparation and mount acknowledgement), fixed host-mode validation, the grant handshake and outer monotonic deadline, screenshot transport, resource cleanup and page recycling. Configure core's `acquire`/`quiesce` hooks for that lifecycle; cancellation must revoke unfinished grants and prevent old work mutating a new owner. Core's cooperative timers do not replace host termination of blocked code. TASK-158 supplies the pending asset inventory and acquisition/decode/upload cooperation; an unresponsive page must never invent an inventory from stale observations. TASK-161 owns CLI selection/input envelopes.

Core's existing browser-context import restrictions also reject `src/render/loading` (relative and package-subpath imports). The resolved graph assertion now uses bundled Vite 7.3.7 for the public root, browser subpath and emitted entry, including the production loading resolver. Negative fixtures exercise Node built-ins and an aliased loading-service module; a separate negative lint test checks core imports. `src` in the tsconfig includes the generators, browser bootstrap, virtual-entry declaration and checked JavaScript child launcher.

## Renderer API

The root is the authoring surface: `@kimuson/motion-kit` resolves to `dist/index.js` (`dist/index.d.ts` for types). The renderer entry is the `./render` subpath (`@kimuson/motion-kit/render`), which exports only `createRenderer` and its public types from `src/render/index.ts` (built to `dist/render.js`). `./agent` is the CLI/agent contract (`src/agent/cli-output.ts`); `./browser` arrives with TASK-190. The loading session and browser bootstrap remain internal; the loader privately resolves `@kimuson/motion-kit/browser`.

Source lives in `src/`; `pnpm build` (tsdown) emits the published ESM and `.d.ts` into `dist/`, and `package.json#exports` points `types`/`import` at `dist`. Development and the repository's tests resolve its own name to `src` through the vitest/tsconfig aliases; `prelint`/`pretypecheck`/`pretest` run `pnpm build` first to make `dist` available. The published package is exercised by publint, attw, the resolved browser-graph check against `dist`, and the built-artifact CLI/renderer route (`src/cli/built-artifact.test.ts`), while the unit/cli/loading/frame-transport tests resolve to `src`.

- `await createRenderer({ projectRoot, entry, compositionId?, props?, loadingTimeoutMs?, queueTimeoutMs?, frameTimeoutMs?, signal?, ...browserOptions })` returns `Result<Renderer>` or `{ ok: false, aborted: true }`. Props are JSON objects, validated once per selection in the page.
- `renderer.renderFrame({ frame, signal? })` returns PNG `Buffer` bytes with `frame`, `width`, `height`, and warning `diagnostics`, only after capture completion accepts the lease. Invalid output frames use the Time Module's `composition.props-invalid`; `location.frame` is supplied only for safe integers.
- `renderer.renderFrames({ from, to, signal? })` is an async iterable of those Results for the **half-open** range `[from, to)`, stopping at the first failure/abort. An empty valid range produces no frames.
- `renderer.select({ compositionId?, props? })` serializes a fresh realm/props revision behind existing frame work while retaining the Vite service. Concurrent frame calls queue in submission order; queued cancellation does not mutate or destroy an active renderer frame.
- Always await `renderer.dispose()` and check its Result, including after an automatically cleaned-up failure. Active failure/cancellation closes the entire owned session rather than reusing a potentially poisoned realm; create a new renderer to retry. Successful frames retain the healthy session until disposal.
- Loading, caller/queue, and frame budgets default independently to **30,000 ms**. The queue budget starts at submission; a validated host ownership grant replaces it with the monotonic frame deadline, before page mutation. Screenshot and final acceptance remain inside that one deadline. Source-version changes discard bytes and re-settle under the same generation/deadline.
- The version-1 promise RPC uses `settleFrame`, `validateCapture`, `resettle`, `completeCapture`, `cancel`, and disposal. `page.exposeFunction` carries validated ownership grants before navigation. Host and page check mode, instance, revision, generation, rational time, frame and resource versions; ready is not release.
- A responsive coordinator's current required-asset inventory at deadline produces `asset.not-ready` with every pending asset and `timeoutMs`. Other deadline expiry, including unresponsive GPU/RPC/capture, produces `render.frame-timeout`; the post-expiry inventory probe is bounded to 100 ms and never authorizes publication. Asset failures preserve `asset.load-failed`. A failed settlement, validation, or completion publishes every diagnostic on `error`; the host does not keep only the first or merge codes. Caller/queue cancellation returns aborted without a Diagnostic or frame. Integration-provided inventory is a neutral TASK-158 cooperation hook, not automatic asset discovery.
- Detected Tier C registrations emit `seek.uncontrolled`; arbitrary hidden clocks are not detected. Exact-byte evidence applies only to supported paths in the tested fixed environment, not every React component or GPU.

## Internal loading session

`src/render/loading/session.ts` supplies `openLoadingSession`, `LoadingSessionOptions`, `LoadingSession`, `Selection` and `LoadingOutcome` to the supervisor. These are not package exports.

- Supply `projectRoot` and an `entry` relative to it. No Vite config, Vite installation or application entry is required. One session owns its Vite process, loopback listener, temporary cache/config bundles, browser and replaceable contexts. Independent invocations do not share them.
- Read `session.compositions`, then call `session.select({ compositionId?, props? })`. Every selection creates a fresh realm, including a props-only change. A successful selection returns an instance identity and descriptor, not a ready frame. Core prepares the React root without rendering scene content or seeking time.
- Loading operations return `Result<T>`; caller cancellation through `options.signal` instead returns `{ ok: false, aborted: true }`, with no Diagnostic. Always await `session.dispose()` and check its Result. The internal session exposes its URL, workspace, service/browser PIDs, connection state and owned page to the supervisor and lifecycle tests; none is exposed on the public Renderer.
- `loadingTimeoutMs` defaults to 30,000. Initial config/server/navigation/handshake/metadata share one budget; each sequential defaults parse and each later props/mount operation gets a fresh full budget. The external supervisor kills a synchronously blocked service process group or an unresponsive owned browser. Normal teardown attempts Vite close before bounded escalation, and removes the entire temporary workspace.
- `disableSandbox` defaults to false; `softwareWebGL` defaults to false. `executablePath` is an explicit launch override. A missing browser yields `render.browser-launch-failed` with `pnpm exec playwright install chromium`, without installation or retry.
- The launcher never takes process signals over: `handleSIGINT`, `handleSIGTERM` and `handleSIGHUP` are `false`, because cancellation belongs to the caller that installs the `AbortSignal`. Playwright's `SIGINT` handler exits the process (`130`) before that caller's asynchronous cleanup can finish, and its `SIGTERM`/`SIGHUP` handlers close the browsers without exiting, which would report a supervisor stop or a closed terminal as a mid-render browser failure instead of a cancellation. Playwright's `exit` handler still kills the processes it tracks. A process exit under a caller's cancellation is guarded by `coverOnExit` (`src/lib/exit.ts`), which kills the encoder and the loading service's process group and removes temporaries synchronously.

The loader runs serve/development, preserving config functions, aliases, plugins, CSS, public assets, base and root. Config evaluation occurs once. The guarded adapter intercepts config externalization before project-relative lookup and subsequent ESM/CommonJS loads; `vite`, `vite/module-runner` and `vite/package.json` resolve to bundled 7.3.7. It rejects detected second-Vite/private-path bypasses. Arbitrary custom loaders and plugin-spawned processes are not adapted or certified.

The loaded user config is passed to the bundled Vite unchanged, except motion-kit's reserved settings, which are overridden after resolution; the [bundled-Vite ADR](adr/20261024-bundled-vite.accepted.md) records which keys still apply in middleware serve mode and how a config, plugin or dependency-optimizer failure is reported. Motion-kit never rejects a key, never maintains a key list, and does not read plugin manifests, peer ranges, or Vite internals. Raw exceptions and stacks never enter a Diagnostic.

Motion-kit owns middleware/custom HTML, loopback listening, bootstrap routes, no auto-open, renderer HMR policy, serve/development mode, ephemeral cache, React/ReactDOM/runtime singleton resolution, the reserved bootstrap/package-entry/user-entry ids (exact-match aliases placed ahead of the project's aliases, so a conflicting project alias is overridden, not rejected) and stderr logging. React comes from the project even for linked packages; the bootstrap comes from the invoking installation. Vite 7 still creates a WebSocket listener with `hmr: false`, so the renderer also sets `ws: false`. A guarded, exact-version client transform suppresses its connection call while retaining Vite's CSS helpers. Detected source/config edits invalidate and close a renderer session; start a fresh session. Preview orchestration is not shipped here.

Tests: `pnpm test --project loading` runs the Chromium config/lifetime/launch matrix; `composition-dom` checks bootstrap preparation and owned settlement; `unit` checks the resolved browser graph and lint negatives; `frame-transport` checks PNG pixels, traversal comparisons, leases, deadlines and OS teardown. All four run in CI, with Chromium provisioning; the `frame-transport`, `encoding` and `cli` projects additionally need FFmpeg (see [Encoding](#encoding)), because `src/render/render-video.test.ts` runs in `frame-transport` and spawns `ffmpeg` and `ffprobe`. [Transport evidence](knowledge/20261024-frame-transport.md) records the comparison and mutation matrix.

`src/**/*.determinism.test.ts` is the Phase 1 determinism suite, included in `frame-transport` and excluded from `unit`. `defineDeterminismSuite({ composition, frames })` plus `runDeterminismSuite` (`src/render/determinism/suite.ts`) captures a Composition module through `createRenderer` and compares PNG bytes. The seven modes are sequential 0..N then N, a random order containing N, reverse, repeated N, fresh realm, held session, and N alone in a fresh renderer. Exact bytes are the default. A tolerance is valid only as `{ purpose: 'cross-environment', maxDifferentBytes }` at the call site. Later contexts register a reference Composition by adding a `*.determinism.test.ts` that calls the suite; capture identity is host PNG bytes, so the suite does not run inside the browser-mode project. Hung GPU fences and Linux qualification are CI/platform work, not this suite. Encoding and the CLI are separate concerns, documented in the sections below.

## Encoding

The [accepted encoding decision](adr/20261025-system-ffmpeg-encoder.accepted.md) fixes the Phase 1 encoder; TASK-159 implements it and wires the CLI. `src/render/encoding` owns the port and the whole subprocess boundary.

- Phase 1 encodes H.264/MP4 with **`ffmpeg` from the user's `PATH`** (or an explicit `ffmpegPath`). motion-kit bundles and downloads no binary and takes no encoder package dependency; a working FFmpeg 6.0+ with `libx264` is a documented prerequisite, probed once per invocation.
- `Encoder.encode({ frames, fps, frameCount, output, signal?, onProgress? })` consumes `AsyncIterable<FrameCaptureResult>` — the stream `renderFrames` already yields, PNG bytes per frame — with `frameCount` taken from the Composition descriptor's `durationInFrames`, and returns `Result<EncodeReceipt, readonly Diagnostic[]>` or aborted control flow. The port does not reopen the frame transport or accept a file layout instead. A successful receipt carries the encoded frames' warnings (`seek.uncontrolled`, `layout.*`) in frame order, and the CLI reports them on the `mp4` envelope exactly as the frames route reports them, so a successful encode is not a warning-free one.
- FPS crosses as the Composition's rational and reaches FFmpeg as `numerator/denominator`, never a float; the receipt's duration comes from the Time Module. The target is written to a temporary sibling, created before the child starts and renamed only on success, so no partial file appears at `output` and an unwritable destination fails before FFmpeg runs. The child runs with overwrite enabled (`-y`), because FFmpeg cannot prompt while stdin is the frame pipe and would otherwise refuse the sibling it finds.
- The caller's `AbortSignal` is the only cancellation source, and it covers the whole boundary: the probe children (`ffmpeg -version`, `-encoders`) are killed by it too, so a cancelled `createFfmpegEncoder` returns aborted control flow instead of a Diagnostic. A cancellation that arrives after the last frame was handed over still kills a child that is finishing on its own, so no encoder child outlives the command.
- Encoder failures are `encode.ffmpeg-not-found` (missing binary), `encode.ffmpeg-unsupported` (too old or no `libx264`), `encode.ffmpeg-failed` (non-zero exit after at least one frame), and `encode.output-invalid` (no usable output: zero frames, an unwritable target directory, or a zero-byte temporary sibling after a successful exit), each with one corrective hint — only the missing binary names per-OS install commands. A failed capture frame ends the encode with that frame's Diagnostics, never as an FFmpeg failure; an aborted element from a caller-assembled stream ends it as aborted control flow with no Diagnostic; a stream that ends before `frameCount` without a failed frame is `internal.unexpected`, not a success.
- **Audio** is the Composition's own data (`audio: readonly AudioTrack[]` on `defineComposition`), carried to Node on the descriptor and resolved against the project root ([audio muxing ADR](adr/20261026-audio-track-muxing.accepted.md)). The encoder muxes every declared clip in the same child invocation: one `-i` per track, a filter graph that trims (`atrim`), gains (`volume`), resamples to 48 kHz (`aresample`), converts to stereo per source channel count (`pan=stereo|c0=c0|c1=c0` for mono, `aformat=…:channel_layouts=stereo` otherwise), places at the frame-derived offset (`adelay`, integer ms), sums (`amix … normalize=0`) and pads with silence (`apad`), then `-c:a aac -b:a 192k`. The channel count comes from one `ffprobe` per declared track (the FFmpeg install provides it; a silent render spawns nothing), so a mono clip keeps the file's own level instead of FFmpeg's −3.01 dB constant-power upmix and `volume: 1` is unchanged for every format. The output `-t` is the Time Module's `frameCount / fps`, so the audio stream ends with the frames instead of `-shortest` truncating the video. A `src` that is missing, not a regular file or not openable is `asset.load-failed` with the redacted source in `location` and `details.assets`, reported before the temporary sibling exists and before the encode child starts. A request with no audio declarations spawns exactly the video-only arguments, so the silent path is unchanged. In-browser preview audio and audio-reactive visuals are not implemented.
- `Encoder` and its request/receipt types stay internal to `src/render/encoding` and are not `./render` exports.
- Encoding in the capture page with WebCodecs and Mediabunny is a Phase 5 experiment, not Phase 1.

Tests: `pnpm test --project encoding` covers the probe matrix and every post-probe failure against a stand-in binary, plus one real encode probed with `ffprobe`; it also pins the silent argument vector and, for declared audio, the one-input-per-track argument list, the mix graph and the pre-spawn `asset.load-failed`. `frame-transport` runs `src/render/render-video.test.ts`, which mounts a 2-second Composition, encodes its frame stream and checks the file's frame count, rate, duration, codec and decoded first/last frames against the captured PNGs, plus a 3-second audio fixture whose two generated clips are checked on `ffprobe` (AAC 48 kHz stereo, 3 s) and by energy onsets within one frame of the declared offsets and a 0.5 gain. Both need `ffmpeg` and `ffprobe` on `PATH` and fail without them — no case skips — and CI installs FFmpeg and asserts `libx264` before running them, plus the CLI's `.mp4` case in `--project cli`. Test audio is generated by FFmpeg into a temporary directory and never committed.

## Trust model

Render executes the user's own project code with the invoking user's privileges, like Vite or a test runner. The [Phase 0 ADR](../../decisions/20261024-time-control-and-frame-capture.accepted.md#capture-environment-and-gpu-baseline) fixes this Phase 1 boundary: Chromium's sandbox is on by default, with container opt-out only through an explicit option; software-WebGL flags are explicit opt-ins. Suppress Playwright defaults that disable the sandbox or enable unsafe software WebGL.

Composition page/iframe separation protects clock/state ownership, not host security. Vite config/plugins execute trusted Node code. Page access uses only the Vite-served project/referenced-asset and bootstrap scope; there is no added filesystem, process or arbitrary-evaluation page RPC. That scope is not an access-control guarantee against trusted code. No untrusted mode, OS-level job isolation or network policy is implemented in Phase 1. Untrusted rendering is TASK-176, parked, **do not start**.
