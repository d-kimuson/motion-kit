# Distribute `@kimuson/motion-kit` on npm only, and publish it with Trusted Publishing

## Context

Status: **accepted**.

motion-kit has been developed from a checkout and never published: `package.json` was `private`, the version `0.0.0`, and the README says the commands run from a clone. TASK-224 writes the consumer-facing install path, TASK-225 performs the first publish, and this decision fixes what both build on.

The forces:

- **One registry, no second channel.** The package is a Node-side library and a CLI (`bin`, three subpath exports over `dist/`); a consumer reaches it with `npm install`/`npx`, not through a CDN. A self-hosted mirror or GitHub Packages would add a second place to keep in sync and, for GitHub Packages, a scope and auth in front of a public package.
- **No long-lived credential.** The repository has exactly one maintainer, so an `NPM_TOKEN` secret is a credential to leak and rotate with nobody watching; and since the repository is public, that secret would sit in a workflow anyone can read. npm Trusted Publishing exchanges a GitHub OIDC identity for a token that lives for one job.
- **The trust contract is the workflow file.** npm's trusted publisher names the repository and the workflow _filename_ (`.github/workflows/release.yml`), and the npm CLI sends `repository.url` with the publish; a mismatch fails the publish. Renaming the workflow, moving the repository, or publishing from a fork breaks trusted publishing until the npm configuration is updated.
- **A package must exist before a trusted publisher can be configured.** npm configures a trusted publisher in the package's settings, so the first version of a new package can only be published by hand. A newly created trusted publisher configuration then has **2 days** to complete its first successful OIDC publish; past that it expires and has to be deleted and recreated.
- **Provenance follows from a public repository.** npm generates a provenance attestation automatically for an OIDC publish when the package is public _and_ the source repository is public ([npm's trusted-publishing page](https://docs.npmjs.com/trusted-publishers), [npm: generating provenance](https://docs.npmjs.com/generating-provenance-statements)). The repository is public as of 2026-10-28, so a CI publish is attested without asking for it; only the manual first publish, which does not go through OIDC, carries none.
- **Prereleases are how a build gets tried.** A release that has to be exercised before it becomes `@latest` needs a dist-tag that does not move `latest`.
- **The published tree is build output, the user docs and the third-party notice.** `dist/` is generated by tsdown from `src/` and is not committed; the consumer-facing documentation is `docs/index.md` and `docs/guide`, written by TASK-224 and shipped so a reader can stay off the repository; `THIRD_PARTY_LICENSES.md` is generated from the runtime dependencies and committed so that every tarball carries it. None of them carries `scripts`, `devDependencies` or `packageManager` to consumers. _Amended 2026-10-29 (TASK-227): added the third-party notice to the published tree._

## Decision

**npm is the only distribution.** The repository root's `package.json` is published as `@kimuson/motion-kit` on the public npm registry. `files: ["dist", "docs/index.md", "docs/guide", "THIRD_PARTY_LICENSES.md"]` limits the tarball to the tsdown build, the user documentation and the third-party notice, and npm adds `package.json`, `README.md` and `LICENSE`. There is no other registry, no mirrored copy, and no committed build output. _Amended 2026-10-29 (TASK-227): added `THIRD_PARTY_LICENSES.md` to `files`._

**Publishing is Trusted Publishing only, with no token anywhere.** `.github/workflows/release.yml` runs on `v*` tags with `permissions: { contents: read, id-token: write }`, installs from the frozen lockfile with `--ignore-scripts` as `check.yaml` does (a dependency's install script must not run inside the job that can mint the publishing identity), and publishes with `npm publish`. The npm CLI bundled with the Node in `.node-version` performs the OIDC exchange, so no `NPM_TOKEN` secret, no `.npmrc` token, and no `pnpm publish` (whose git and provenance handling is a second implementation of the step that must be npm's). GitHub-hosted runners only; self-hosted runners are not supported by npm.

**The first publish is manual and the configuration has a deadline.** `@kimuson/motion-kit@0.0.0` is published by hand from a clean checkout of the release commit. The owner then configures the trusted publisher for `d-kimuson/motion-kit`, workflow `release.yml`, allowed action `npm publish`, and the next release (`0.0.1`) must publish through the workflow within 2 days or the configuration expires. The steps are in [`docs/guidelines/release.md`](../guidelines/release.md).

**Provenance is npm's default, not an option.** `publishConfig` carries only `access: public`, and the workflow passes no `--provenance`: the package is public and the repository is public, so npm generates the attestation from the OIDC exchange the publish already performs. Leaving the flag off keeps one way to ask for an attestation rather than two. The manual first publish has none, because it is not an OIDC publish.

**The version is the source of truth for the tag.** `npm version <spec>` runs the `preversion` script (lint, typecheck, test, build), writes the version, and creates the signed commit and the signed `v<version>` tag. The workflow refuses a tag that does not equal `package.json#version`, so a `v0.0.2` pushed by hand against `0.0.1` fails before anything reaches the registry.

**Prereleases go to their own dist-tag.** A tag with a prerelease suffix resolves to the dist-tag of its identifier — `v0.1.1-beta.0` publishes under `beta`, `v2.0.0-rc.3` under `rc` — and every other tag publishes under `latest`. `@latest` therefore only ever resolves to a release, and a prerelease is installed explicitly with `@kimuson/motion-kit@beta`.

**The release job builds and strips from the tag.** It runs `pnpm build`, then `pnpm exec clean-pkg-json`, which removes `scripts`, `devDependencies` and `packageManager` from `package.json` in the workspace before `npm publish` reads it. The strip lives in the workflow, not in a `prepublishOnly`/`prepare` script, so a local `pnpm pack` still shows the development fields and no local command can publish a half-cleaned package by accident.

**`engines.node` is `>=22.14.0`; the npm CLI floor is a publish-time check, not an engine.** The declared floor is the Node version Trusted Publishing itself requires, so the oldest supported consumer Node and the release job agree on one number. The npm CLI requirement (11.5.1 or later) belongs to the release job, which asserts it before publishing: Node 22.14.0 ships npm 10.9.2, so the bundled CLI is checked rather than assumed, and `npm` is kept out of `engines` because it would warn every consumer who installs with an older npm for a requirement only the release job has.

**`repository` is exact.** `repository.url` is `git+https://github.com/d-kimuson/motion-kit.git` and must stay equal to the GitHub repository the trusted publisher names; `homepage` and `bugs` point at the same repository.

## Consequences

A release is a version bump, a signed tag and a workflow run — there is no token to store, no publish script to maintain, and nothing on a maintainer's machine that can publish. The published bytes are built from the tag by the same commands a local checkout uses, and `clean-pkg-json` guarantees the tarball carries no development-only fields.

The costs are explicit:

- A CI release is attested and the manual `0.0.0` is not. The provenance statement binds a tarball to the workflow run and the commit that produced it; a version published from a laptop has nothing to bind, and stays unattested for good.
- The first publish and the 2-day validation window cannot be automated away. A missed window means deleting and recreating the trusted publisher, not a retry.
- The workflow filename and the repository identity are part of the publishing contract. Renaming `.github/workflows/release.yml`, moving the repository, or publishing from a fork fails with `ENEEDAUTH` until the npm configuration matches — and npm does not validate the configuration when it is saved, only when a publish arrives.
- A published version is spent. `npm unpublish` is restricted, so a defect in a release is fixed by the next version, never by replacing the tarball. `@kimuson/motion-kit@<version>` stays resolvable and unchanged.
- The release job is the only place that can publish, so a broken `release.yml` blocks every release until it is fixed on `main`; it cannot be rehearsed by a pull request, because it only triggers on tags.

## Alternatives

- **An `NPM_TOKEN` repository secret with `pnpm publish`:** works from a fork and from a laptop, and needs no npm configuration, but it is a long-lived credential in a repository with one maintainer to rotate it, and it makes every workflow run a publishing run.
- **Configure the trusted publisher and let the workflow publish the first version itself:** impossible — npm only offers the trusted-publisher form on a package that already exists.
- **Keep `private: true` and tell consumers to use the repository:** the README already has to explain a checkout, and a consumer cannot `npm install` a private workspace package; TASK-224 needs a registry.
- **Commit `dist/` and publish without building in CI:** the tarball would be whatever the last committer built, and every review of a release would include build output.
- **Publish `latest` for prereleases too:** a beta would become what every `npm install @kimuson/motion-kit` resolves to, and pulling it back is another release.
- **Publish on every push to `main` with a version derived from the commit:** the version would not be a reviewed value, and a merge would publish without anybody deciding to release.
- **GitHub Packages or a self-hosted registry:** a public package that a consumer must configure a scope and credentials for, and a second distribution to keep in sync with npm.
